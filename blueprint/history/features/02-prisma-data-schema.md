# Feature: Prisma data schema

**From build-plan:** feature 2
**Build attempt:** 1
**Status:** verified
**Branch:** feature/prisma-data-schema

## Goal

Migrate the five core models (`Template`, `TemplateTask`, `TemplateRecurrence`,
`DailyPlan`, `DailyTask`) from the project overview's data model into a real
Prisma schema and an applied PostgreSQL migration, with a shared Prisma Client
instance the app can import, so every later feature has a working data layer.

## In scope

- The five models in `prisma/schema.prisma`, matching the overview's fields
  exactly, with explicit relation, cascade, and uniqueness behavior (see
  Data / contracts).
- One applied migration against the `DATABASE_URL` already configured in
  `.env` (Prisma Postgres, via Vercel Storage), created with
  `prisma migrate dev`.
- A shared `PrismaClient` singleton at `src/lib/prisma.ts`, instantiated with
  the `@prisma/adapter-pg` driver adapter (required for Prisma ORM 7's
  standard Node.js SQL workflow) and guarded against creating duplicate
  instances across Next.js dev-mode hot reloads.
- Adding `@prisma/adapter-pg` and `pg` as dependencies.

## Out of scope

- Any Route Handler, CRUD UI, or query against these models (feature 3).
- Recurrence-assignment UI, default-template UI, or automatic plan generation
  (features 4-6) - this feature only makes the weekday slot itself
  unique in the schema.
- Seed data - nothing in the plan calls for example rows yet.
- Zod input validation - that applies to Route Handler input in feature 3+,
  not to the schema itself.
- Auth/session/tenant scoping (project has none - single user).

## Data / contracts

```prisma
model Template {
  id          Int                  @id @default(autoincrement())
  name        String
  isDefault   Boolean              @default(false)
  createdAt   DateTime             @default(now())
  tasks       TemplateTask[]
  recurrences TemplateRecurrence[]
  dailyPlans  DailyPlan[]
}

model TemplateTask {
  id            Int      @id @default(autoincrement())
  templateId    Int
  template      Template @relation(fields: [templateId], references: [id], onDelete: Cascade)
  title         String
  suggestedTime String?
  order         Int
}

model TemplateRecurrence {
  weekday    Int      @id
  templateId Int
  template   Template @relation(fields: [templateId], references: [id], onDelete: Cascade)
}

model DailyPlan {
  id         Int         @id @default(autoincrement())
  date       DateTime    @unique @db.Date
  templateId Int?
  template   Template?   @relation(fields: [templateId], references: [id], onDelete: SetNull)
  closed     Boolean     @default(false)
  tasks      DailyTask[]
}

model DailyTask {
  id            Int       @id @default(autoincrement())
  dailyPlanId   Int
  dailyPlan     DailyPlan @relation(fields: [dailyPlanId], references: [id], onDelete: Cascade)
  title         String
  suggestedTime String?
  completed     Boolean   @default(false)
  completedAt   DateTime?
  order         Int
}
```

Decisions made to keep every relation and constraint explicit, for review:

- **`id` fields are plain autoincrementing `Int`.** No external system consumes
  these IDs and the app has no multi-tenant or public-API exposure that would
  need opaque/globally-unique IDs (per the overview's usage model), so the
  simplest option applies.
- **`TemplateRecurrence.weekday` is the primary key, not a surrogate id.**
  This makes "one weekday, at most one template" a schema-level guarantee.
  The overview's feature 6 line - "creates one from the matching template" -
  is singular, which only holds if a weekday can't be claimed by two
  templates at once. Feature 4's recurrence-assignment UI must therefore
  reassign (not duplicate) a weekday already claimed elsewhere; that UI
  behavior belongs to feature 4, not this one.
- **`weekday`'s 0-6 range is not a DB-level `CHECK` constraint.** Prisma has
  no native range-constraint syntax and the codebase's existing pattern
  validates Route Handler input with Zod (`coding-standards.md`); that
  validation belongs to the feature that writes these rows (feature 4).
- **`DailyPlan.date` is `@db.Date`, not a full timestamp.** The overview
  calls it "one plan per calendar day"; storing only the date avoids
  timezone-dependent duplicate-day bugs.
- **`Template` -> `DailyPlan` is `onDelete: SetNull`, not `Cascade`.** The
  overview states `DailyPlan`/`DailyTask` are the immutable historical
  record once `closed`; deleting a template must never delete history, only
  detach the now-dangling reference.
- **`Template` -> `TemplateTask`/`TemplateRecurrence` and `DailyPlan` ->
  `DailyTask` are `onDelete: Cascade`.** Both children have no independent
  existence outside their parent.

### 2/F-01 [P1] closed - No `prisma generate` step, so a fresh clone or CI build cannot compile

**File:** package.json:7
**Found:** 2026-09-22 by /audit (scope: current; lens: quality)
**Why it matters:** `src/lib/prisma.ts:1` imports `@/generated/prisma/client`,
which resolves to `src/generated/prisma/`. That directory is gitignored
(`.gitignore:43`, confirmed with `git check-ignore -v`) and is not produced by
`npm install`: Prisma ORM 7 removed postinstall auto-generation, which the
project's own reference confirms by listing `PRISMA_GENERATE_IN_POSTINSTALL` and
`PRISMA_SKIP_POSTINSTALL_GENERATE` as removed
(`.claude/skills/prisma-upgrade-v7/references/env-variables.md:127-128`), and the
CLI reference states `prisma generate` must run "before building your
application" in CI/CD (`.claude/skills/prisma-cli/references/generate.md:118-126`).
`package.json` has no `postinstall`, `prebuild`, or `generate` script, and there
is no `vercel.json` build-command override. `npm run build` passes here only
because a previously generated client already sits in the working tree. On any
fresh checkout, CI runner, or the Vercel deployment named in
`project-overview.md`, `npm ci && npm run build` fails with an unresolved
`@/generated/prisma/client` import. This feature introduces the break: it is the
first tracked file to import the generated client. `AGENTS.md` declares
`npm run build` as a project command, so the contract is that it works from a
clean checkout.
**Suggested fix:** Add a generate step that runs before the build, for example
`"prebuild": "prisma generate"` (or fold it into `"build": "prisma generate &&
next build"`) in `package.json`. That is the smallest change that makes the
declared Build command reproducible; no new dependency or config surface is
needed since `prisma` is already a devDependency. Committing the generated output
instead would work but contradicts `.gitignore:43`.
**Resolution:** Added `"prebuild": "prisma generate"` to `package.json`
(build step 4). Verified by removing `src/generated/prisma` and re-running
`npm run build`, which regenerated the client before `next build` and passed;
a second `npm run build` with the client present also passed.
Closed by independent review 2026-09-22 (fresh subagent, target f9031b2).

### 2/F-03 [P3] closed - `DATABASE_URL` is passed to the adapter without a fail-fast check

**File:** src/lib/prisma.ts:8
**Found:** 2026-09-22 by /audit (scope: current; lens: quality)
**Why it matters:** `process.env.DATABASE_URL` is typed `string | undefined` and
`pg.PoolConfig.connectionString` accepts `undefined`, so this typechecks and the
build passes. If the variable is absent (a new clone with no `.env`, or a Vercel
environment where it was not set), `pg` silently falls back to libpq defaults and
attempts a local connection, so the first query fails with an opaque connection
error pointing at localhost instead of naming the real cause. `project-overview.md`
lists `DATABASE_URL` as the single required env var, which makes a clear failure
message worth the one line.
**Suggested fix:** Read the variable once into a local and throw when it is
missing, for example `const connectionString = process.env.DATABASE_URL; if
(!connectionString) throw new Error("DATABASE_URL is not set");` before
constructing `PrismaPg`. No validation library is needed.
**Resolution:** Added the exact suggested check in `src/lib/prisma.ts` before
constructing the adapter (build step 4). Covered by the same `npm run build`
evidence as F-01 (typechecks cleanly).
Closed by independent review 2026-09-22 (fresh subagent, target f9031b2).
`src/lib/prisma.ts:8-10` now guards with `if (!process.env.DATABASE_URL) {
throw new Error("DATABASE_URL is not set"); }`, which runs before the adapter
is constructed at line 12, so an unset or empty value now fails with the real
cause instead of an opaque libpq/localhost connection error. The message names
only the variable and never prints its value, so no secret is exposed.
Typechecking is clean and the file is genuinely in the program:
`npx tsc --noEmit --listFiles` lists `src/lib/prisma.ts`, and
`npx tsc --noEmit` exits 0, so the guard's narrowing does not break the rest
of the file. `npm run lint` also exits 0. The guard is a module-scope throw, so
the first module that imports this file inherits fail-fast behavior at import
time; nothing imports it yet (only `src/lib/prisma.ts` references the generated
client), so there is no build-time or prerender regression in this delta.

**File:** blueprint/context/project-overview.md:75
**Found:** 2026-09-22 by /audit (scope: current; lens: quality)
**Why it matters:** The overview calls `TemplateRecurrence` a "many-to-many join

generation. Leaving both statements in place invites a later feature to assume two
templates can share a weekday.
**Suggested fix:** Update the `TemplateRecurrence` bullet in
`project-overview.md` to say one template per weekday, with `weekday` as the
primary key. This is a user-owned planning doc, so the wording change needs the
user's approval rather than an automatic edit.
**Resolution:** User approved the wording change. Updated the
`TemplateRecurrence` bullet in `project-overview.md` to state `weekday` is
the primary key and that each weekday maps to at most one template.
Closed by independent review 2026-09-22 (fresh subagent, target f9031b2).
`blueprint/context/project-overview.md:74` now reads "`weekday` (int, 0-6) -
primary key, so each weekday maps to at most one template", which matches the
shipped design at `prisma/schema.prisma:35` (`weekday Int @id`) and
`prisma/migrations/20260922152321_init/migration.sql:27-31`
(`CONSTRAINT "TemplateRecurrence_pkey" PRIMARY KEY ("weekday")`). The
contradictory "many-to-many join" line is gone: `grep -rn "many-to-many"
blueprint/` now matches only this finding's own text, not the overview. The

`TemplateRecurrence`") stays correct under the one-to-many reading, and the
edit touched only that one bullet, so it introduced no other drift.
